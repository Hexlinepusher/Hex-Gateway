# 模板使用说明

Hex-Gateway 用于在本地接入和试验上游服务。模板提供下游接口、消费者调度、控制台和统一日志，具体服务负责资源管理、上游通信及请求与响应转化。

- [命令速查](Commands.md)：安装、启动、停止与检查命令
- [适配需求清单](适配需求清单.md)：接入上游前需要确定的设计问题
- [技术栈](TechStack.md)：运行环境与开发工具

## 启动配置

在项目根目录按 [.env.example](../.env.example) 创建 `.env`，通过 Docker 或 Node.js 启动。网关监听 `0.0.0.0`，默认端口为 `8800`；本机可访问 `http://localhost:8800/` 打开控制台。

| 环境变量                        | 用途                             | 默认值                 | 服务收到的配置字段 |
| ------------------------------- | -------------------------------- | ---------------------- | ------------------ |
| `PORT`                          | HTTP 监听端口                    | `8800`                 | `port`             |
| `GATEWAY_API_KEY`               | 下游访问网关的 API Key           | 空值                   | `apiKey`           |
| `UPSTREAM_SERVICE_NAME`         | 上游服务名，用于生成固定模型 ID  | `default_service_name` | `serviceName`      |
| `REQUEST_QUEUE_CAPACITY`        | 等待与锁定条目的总容量           | `32`                   | `queueCapacity`    |
| `RETRY_TIMES`                   | 首次执行之外允许的重试轮次       | `0`                    | `retryTimes`       |
| `REQUEST_IDLE_TIMEOUT_SECONDS`  | 每次上游调用的空闲超时，单位为秒 | `300`                  | `idleTimeoutMs`    |
| `REQUEST_TOTAL_TIMEOUT_SECONDS` | 每次上游调用的整体超时，单位为秒 | `600`                  | `totalTimeoutMs`   |

配置在启动时读取。传给具体服务的两个超时字段已换算为毫秒，其余字段与上表对应。

模板默认提供空消费者列表，具体服务负责提供执行函数。此时可以使用控制台、健康检查、模型列表和测试模型；普通模型请求入队后，会等待消费者可用、下游取消或网关关闭。

## 下游接口

| 方法   | 路径                   | 用途                                                       |
| ------ | ---------------------- | ---------------------------------------------------------- |
| `GET`  | `/`                    | 打开控制台                                                 |
| `GET`  | `/health`              | 返回 HTTP `200` 和 `{"status":"ok"}`，表示网关自身正常运行 |
| `GET`  | `/v1/models`           | 查询模型清单                                               |
| `POST` | `/v1/chat/completions` | 使用 OpenAI Chat Completions 协议对话                      |
| `POST` | `/v1/messages`         | 使用 Anthropic Messages 协议对话                           |

查询模型列表时，请求带有 `anthropic-version` 头则返回 Anthropic 格式，其余情况返回 OpenAI 格式。

### 鉴权与请求校验

`GATEWAY_API_KEY` 非空时，模型列表和两个对话接口要求匹配密钥，支持 `Authorization: Bearer <密钥>` 或 `x-api-key`。配置为空时，未传密钥或传入任意密钥均可通过。首页、健康检查、静态资源及控制台查询和重置均免鉴权。

对话入口检查请求体是 JSON 对象、`model` 是非空字符串且属于模型清单，以及 `stream` 在提供时是布尔值。OpenAI 请求允许 `stream: null`，模板不改写该值。其余业务参数保留原值，交给具体服务处理。

普通请求排队不设超时。HTTP 层不设置请求接收超时和套接字活动超时，请求头接收与连接复用等待使用 Node.js 的默认设置。上游调用的计时方式见[每次上游调用的超时](#每次上游调用的超时)。

### 本地测试模型

`<服务名>-test` 在本地返回 `OK`，按请求协议和 `stream` 参数生成非流式响应或流式事件，token 用量为 `0`。测试模型不进入队列，不占用消费者，也不产生执行统计。

模板先返回 `OK`，响应完成后异步保存请求。请求已完整接收并识别为测试模型后，即使下游在响应完成前断开，也继续保存。保存失败只记录 `test.save_failed`；网关关闭时，等待已接收测试请求的保存完成或失败。

记录位于 `data/test_history/`，使用进程本地时间命名为 `YYYY-MM-DD-HH-mm-ss.txt`；同秒重名追加 `-001`、`-002` 等序号，不覆盖已有记录。

记录包含 Node.js HTTP 层收到的方法、目标地址、HTTP 版本、请求头和完整请求体。请求头保留顺序、大小写及访问凭证，请求体保留原始字节；分块编码等网络封装已由 HTTP 层解析。

### 本地错误响应

错误内容按调用方使用的 OpenAI 或 Anthropic 协议封装。响应已经开始时，通过流内错误或中断结束，无法再更改 HTTP 状态码。

| 场景                           | HTTP 状态                   | message                         | 日志事件                                                      |
| ------------------------------ | --------------------------- | ------------------------------- | ------------------------------------------------------------- |
| 请求体格式错误                 | `400 Bad Request`           | `Invalid Request Body`          | `request.rejected`                                            |
| API Key 校验失败               | `403 Forbidden`             | `Invalid API Key`               | `request.rejected`                                            |
| 模型 ID 不存在                 | `404 Not Found`             | `Invalid Model ID`              | `request.rejected`                                            |
| 地址、静态资源或重置指标不存在 | `404 Not Found`             | `Resource Not Found`            | `request.rejected`                                            |
| 请求方法不匹配                 | `405 Method Not Allowed`    | `Invalid Request Method`        | `request.rejected`                                            |
| 队列容量已满                   | `429 Too Many Requests`     | `Out of Request Queue Capacity` | `request.rejected`                                            |
| 重试次数已用尽                 | `429 Too Many Requests`     | `Retry Limit Exceeded`          | `request.terminated`                                          |
| 内部执行异常                   | `500 Internal Server Error` | `Internal Execution Error`      | `execution.failed`；下游已取消时使用 `execution.safefinished` |
| 网关关闭                       | `503 Service Unavailable`   | `Gateway Is Stopping`           | `request.terminated`                                          |

`405` 响应包含 `Allow` 头。

## 控制台

首页展示运行概览和独立的模型列表。页面打开时读取两者，此后每 5 秒刷新概览；模型清单只在页面加载时读取一次。

| 项目                | 含义                                                          |
| ------------------- | ------------------------------------------------------------- |
| 服务名              | `UPSTREAM_SERVICE_NAME` 配置的名称                            |
| 队列长度            | 当前条目数 / 队列容量，包含等待和锁定中的请求                 |
| 可用消费能力        | 空闲可用消费者数 / 全部可用消费者数，分母包含忙碌的可用消费者 |
| 上游平均延迟（72H） | 每轮执行从锁定请求到首次收到上游数据的平均耗时                |
| 请求平均耗时（72H） | 每轮执行从锁定请求到结束的平均耗时                            |
| 请求成功率（72H）   | 成功执行次数 / 总执行次数                                     |

三个指标均以消费者每次锁定请求后的一轮执行为单位，排队时间不计入耗时。同一请求再次执行时，产生新的样本；一轮内调用上游的次数不改变样本数量。模型列表、健康检查、测试模型和控制台操作不产生样本。

统计在本轮结束后更新，统一归入结束当天的 UTC 日期，保留今天和前两天。日期变化后淘汰最旧一天；进程重启后清空全部统计。每天的结果分为成功、失败、未知异常，总执行次数为三类之和，下游取消后的执行仍按实际结果记录。

首次收到上游数据时记录延迟值，本轮结束后再计入平均值；即使随后执行失败，该延迟值仍保留，始终未收到数据则不产生延迟样本。两个耗时值显示为整数毫秒，无样本时显示 `—`；成功率显示一位小数，无样本时显示 `??%`。

每个指标末尾的按钮只重置该项统计。成功率重置会清空三天结果表；重置延迟或耗时时，只清空相应指标的已有统计。正在执行的请求继续运行，结束后正常计入。操作失败时，页面保留已有数据并显示提示。

## 接入入口

在 [src/service.js](../src/service.js) 中实现 `createService({ configuration, dataDirectory, log, shutdownSignal })`。该函数可以异步初始化，完成后返回服务对象。

| 参数             | 用途                                              |
| ---------------- | ------------------------------------------------- |
| `configuration`  | 启动配置，字段与单位见[启动配置](#启动配置)       |
| `dataDirectory`  | 数据目录的绝对路径，默认指向项目根目录的 `data/`  |
| `log`            | 统一日志函数，调用形式为 `log(event, parameters)` |
| `shutdownSignal` | 网关关闭通知，与执行函数收到的信号相同            |

| 返回字段或方法                        | 用途                                       |
| ------------------------------------- | ------------------------------------------ |
| `additionalModels`                    | 附加模型数组                               |
| `consumers`                           | 消费者数组                                 |
| `execute(context)`                    | 执行本轮请求，完成后返回执行结果           |
| `setConsumersChangedHandler(handler)` | 按需提供，同步保存模板传入的消费者变更回调 |
| `closeResources()`                    | 持有需主动释放的资源时提供，允许异步完成   |

服务分别实现下游请求转化、上游通信和上游响应转化，由 `execute` 组合调用。上游资源管理负责凭证、账号及消费者；文件读写通过统一的[磁盘 I/O 模块](../src/backend/README.md#storage--磁盘读写)完成。

服务初始化失败时，先清理自己已经创建的资源，再抛出错误。初始化成功后若其他启动步骤失败，模板会等待 `closeResources()` 完成清理，再报告启动失败。

### 模型

`additionalModels` 随具体服务在代码中修改，每项必须包含 `id`，可选 `displayName`、`created` 和 `ownedBy`。`created` 使用 Unix 秒，未知时为 `0`；模型 ID 不得重复。

模板根据上游服务名生成 `<服务名>-default` 和 `<服务名>-test`，再与附加模型组成调用白名单。普通模型与上游资源的映射由下游请求转化实现，测试模型由模板处理。

### 消费者

每个消费者包含 `id` 和 `available`，一个消费者对应一个执行名额。多个消费者可以共用账号或凭证，关联方式由具体服务维护。

资源管理负责 `available`，只有 `true` 表示可用。占用字段 `currentExecution` 由模板管理，服务无需修改。

资源管理在同一份 `consumers` 数组中新增消费者或修改其可用状态，然后调用已登记的变更回调，通知模板检查是否可以继续派发请求。多个消费者共用的账号失效时，资源管理应同步停用关联消费者。

## 执行接口

### 执行上下文

`execute(context)` 接收以下字段和操作：

| 字段或操作                                          | 用途                                                       |
| --------------------------------------------------- | ---------------------------------------------------------- |
| `uid`                                               | 请求整个生命周期内保持不变的内部标识                       |
| `attempt`                                           | 从 `1` 开始递增的执行轮次                                  |
| `consumer`                                          | 本轮占用的消费者                                           |
| `request`                                           | 包含 `body`、`protocol`、`method`、`url` 和 `headers`      |
| `shutdownSignal`                                    | 网关关闭通知，下游取消不会触发此信号                       |
| `startUpstreamCallTracking({ onTimeout, onError })` | 实际调用上游时开始计时，返回本次调用的跟踪对象             |
| `recordUpstreamData(upstreamCall)`                  | 收到上游数据时调用，重置空闲计时并记录本轮首次数据到达时间 |
| `finishUpstreamCallTracking(upstreamCall)`          | 本次调用结束时清理计时，允许重复调用                       |
| `deliverStreamEvent({ event, data })`               | 写出一个下游流事件，服务须等待其完成                       |

`request.body` 是解析后的业务 JSON，`request.protocol` 为 `openai` 或 `anthropic`。服务按下游选择的协议和响应形式进行转化；例如，上游只支持流式时，下游的非流式请求需要由服务收集、拼接上游响应后返回。

### 返回结果

服务完成本轮执行及自身 I/O 收尾后，返回以下结果对象：

| 字段               | 用途                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| `outcome`          | `succeeded`、`failed` 或 `unknown`，由服务的响应处理协议判定           |
| `retryRequested`   | 可选布尔值，表示希望再次派发，仍须满足模板的重试条件                   |
| `response`         | 本轮结束时使用的响应；请求重试时也须提供，供不能再次派发时返回         |
| `reason`           | 结果为 `failed` 时必须提供的原因字符串                                 |
| `upstreamResponse` | 结果为 `unknown` 时必须提供实际的 `{ code, status }`，用于未知响应日志 |

`response` 使用以下三种结构之一：

| 结构                   | 用途                                                           |
| ---------------------- | -------------------------------------------------------------- |
| `{ body, statusCode }` | 已转成下游协议且可序列化为 JSON 的响应体；状态码省略时为 `200` |
| `{ error }`            | 错误对象，包含 `message`，可选 `statusCode`、`code` 和 `type`  |
| `{ streamed: true }`   | 服务已写完流事件和协议结束标记，通知模板结束 HTTP 响应         |

流式执行逐次等待 `deliverStreamEvent({ event, data })`。`event` 是 SSE 事件名，Anthropic 使用事件名，OpenAI 可以省略；`data` 为可序列化的 JSON 对象，或需要原样写出的结束标记字符串。服务负责协议内容，模板负责 SSE 序列化与写出。响应开始后发生错误，可通过 `{ error }` 返回流内错误。

### 每次上游调用的超时

实际发起上游调用时，调用 `startUpstreamCallTracking`，同时开始整体和空闲计时。每次收到上游数据调用 `recordUpstreamData`，本次上游响应结束时调用 `finishUpstreamCallTracking`。

每次调用独立计时，空闲计时随数据到达重置，整体计时不重置。调用跟踪结束前，等待下游写入不会暂停这两项计时。

`onTimeout(kind)` 接收 `idle` 或 `total`，由服务决定结束调用、继续等待或请求重试。空闲通知不会停止整体计时；服务继续等待时，后续数据可以重新建立空闲计时。模板只通知超时，不决定错误状态码，也不提前释放消费者。

`onTimeout` 抛错或返回的 Promise 被拒绝时，模板调用 `onError(error)`。服务应立即通知正在等待的上游操作失败，通常调用该操作对应的 Promise 的 `reject`。模板会捕获 `onError` 自身的异常，但不会等待它返回的异步任务；额外的异步处理和 I/O 清理由服务等待完成，再让 `execute` 返回或抛错。

服务应在本轮结束前完成超时处理、调用跟踪和流事件写出。模板会在执行收尾时清理仍登记的计时器。

## 执行与取消

普通请求先入队，空闲且可用的消费者按首次入队顺序锁定尚未锁定的条目。执行中的条目保留在队列内，与等待条目共同占用容量；队列满时拒绝新请求。

服务通过 `retryRequested` 请求再次派发。模板检查本轮是否已经结束、旧消费者是否明确不可用、下游是否仍在等待、响应是否尚未开始，以及网关是否仍在运行。满足这些条件后，再按 `RETRY_TIMES` 检查额外轮次；次数用尽时终结请求，返回 `Retry Limit Exceeded`。

允许再次派发时，模板原位解锁条目，保留 UID 和首次入队顺序，下次锁定时递增 `attempt`。旧消费者仍可用或响应已经开始时，不再派发，使用服务提供的本轮响应结束请求。

下游取消后立即移除队列条目，已经开始的消费者继续执行。模板丢弃后续响应，流事件写出操作正常返回；本轮无论成功、失败还是未知结果，均不再派发，结束后记录 `execution.safefinished`，统计仍使用实际结果。旧轮次的迟到输出和数据通知不会影响新轮次。

## 错误与日志

### 上游结果处理

具体服务根据上游响应码和原因短语维护响应处理协议，识别成功与失败，并确定错误处理方式；未覆盖的响应计为未知异常，一般直接向下游报告。

上游错误默认保留对应的错误状态和内容，特殊处理由服务决定。服务通过 `{ error }` 或 `{ body, statusCode }` 提供结果，模板按下游协议写出；执行结果接口不提供原始响应头、HTTP 原因短语或完整报文的原样转发。`upstreamResponse.status` 用于记录未知响应的原因短语。

服务可使用 [createGatewayError](../src/backend/errors/createGatewayError.js) 的 `createGatewayError(message, { statusCode, code, type })` 构造错误。意外抛错或执行结果未通过结构校验，且没有可用终态结果时，模板按失败结束本轮，使用 `Internal Execution Error` 兜底。业务响应内容及其可序列化性由服务负责。

### 日志调用

各模块通过 `log(event, parameters)` 提交事件，级别和说明模板由[日志事件定义](../src/backend/logging/getLogEventDefinition.js)决定。日志统一使用 UTC 时间，每条占一行，参数中的换行会被转义：

```text
[时间] [级别] [事件标识] 事件说明
```

日志通过终端或 Docker 查看。资源管理负责记录以下消费者状态事件，其他模板事件由相应模块记录。

| 事件                   | 记录时机                 | 参数                     |
| ---------------------- | ------------------------ | ------------------------ |
| `consumer.available`   | 消费者开始可用或恢复可用 | `{ consumerId }`         |
| `consumer.unavailable` | 消费者变为不可用         | `{ consumerId, reason }` |

`consumerId` 使用消费者的 `id`，`reason` 为不可用原因。例如，关闭时将消费者设为不可用后，调用 `log('consumer.unavailable', { consumerId: consumer.id, reason: '网关关闭' })`。完整的事件标识、级别、参数与说明模板见[日志事件定义](../src/backend/logging/getLogEventDefinition.js)。

每轮执行只记录一个结束事件：下游已取消时为 `execution.safefinished`；其余情况按成功、失败或未知响应分别使用 `execution.completed`、`execution.failed`、`execution.unkownresult`。统计始终使用本轮实际结果。

日志格式化或写出失败时，网关继续处理请求，只向标准错误输出一次诊断，并在退出时使用失败状态。

## 网关关闭

使用终端 `Ctrl+C` 或 `docker compose stop` 停止网关。模板停止接收和派发请求，通过共享的 `shutdownSignal` 通知服务收尾；重复停止操作等待同一次关闭。

服务在初始化时登记关闭处理。收到通知后，资源管理同步将消费者设为不可用，并在关闭期间保持该状态；状态变化记录 `consumer.unavailable`，原因为“网关关闭”。执行函数还应检查信号是否已经触发，以免遗漏执行开始前到达的通知。

服务完成当前执行和自身 I/O 清理后，再返回实际结果。模板等待所有执行，包括下游已取消的轮次。完成收尾并解除锁定后，模板清空队列；对尚未开始响应的请求，返回 `Gateway Is Stopping`，已开始的流式响应通过流内错误结束。

关闭还会等待已接收的测试请求保存、剩余 HTTP 响应及服务的 `closeResources()`。尚未形成请求的连接直接断开，已有完整请求按流程收尾。

关闭步骤失败时记录 `gateway.stop_failed`，保持停止状态，继续完成不依赖失败步骤的清理。执行收尾失败时不强行释放消费者或服务整体资源；全部关闭步骤完成后才记录 `gateway.stopped`。

应用不设置关闭期限，本仓库的 Compose 配置无限等待应用收尾；必要时由用户手动强制结束，命令见[命令速查](Commands.md#docker)。
